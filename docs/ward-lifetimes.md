# Наблюдения за вардами из реплея

`ward_lifetimes` — отдельная сохраняемая проекция сущностей Observer/Sentry. Она не заменяет журнал покупок, установок и уничтожений и не моделирует видимость карты.

## Идентичность и время

- Сущность определяется парой `entity_index:entity_serial`. Повторное использование пары после удаления получает отдельный суффикс поколения.
- Владелец определяется по явной ссылке сущности и проверяется против состава матча. Неизвестный владелец остаётся неизвестным.
- `placed_seconds` происходит из `m_flCreateTime`; начало наблюдения хранится отдельно. Реплей может начинаться позже появления сущности.
- Часы берутся из GameRules. В современном формате учитываются `m_bGamePaused`, `m_nPauseStartTick` и `m_nTotalPausedTicks`; голый `NetTick × tick_interval` не используется как запасной источник.
- Время GameRules сохраняется для конкретных наблюдаемых пакетов. Пропуски, скачки часов и лимиты памяти отражаются в покрытии. Они не заполняются интерполяцией.

Проверка на матче `8996432127` выявила паузу в 166 native ticks, примерно 5,53 секунды. Combat timestamps и `m_flCreateTime` исключают эту паузу; сырой NetTick давал бы систематический сдвиг после неё.

## Конец существования

Переход `m_lifeState` фиксирует наблюдаемую смерть. Её время ограничено последним пакетом, где вард наблюдался живым, и первым пакетом с состоянием смерти. Это окно наблюдения, а не обещание точности до миллисекунды.

Удаление сущности хранится отдельно: оно может произойти спустя несколько секунд после смерти. `EntityOpLeft` означает потерю наблюдения, а не смерть. Неизвестный конец не превращается в бесконечный срок жизни. Данные замораживаются при подтверждённом конце игры; послематчевое удаление сущностей не считается смертью в матче.

`alive_at_end` требует явной финальной границы и достаточно свежего наблюдения сущности. Движение варда запрещает показывать весь интервал в одной фиксированной точке.

## Кто уничтожил вард

Сопоставление разрешается только при взаимно однозначном совпадении типа, владельца, команды и точного float32 `m_flLastDamageTime` с событием combat log. Источник помечается `unique-last-damage-match`. Владелец атакующего существа учитывается только при явной атрибуции.

Близость по времени или координатам сама по себе недостаточна. Неоднозначные события и крипы без подтверждённого владельца не получают выдуманного героя-убийцу. Смерть сущности без такого сопоставления остаётся наблюдаемой смертью с неизвестным источником; естественное истечение срока из неё не выводится.

Для слоя девардинга координаты добавляются существующему событию, без создания второго события и изменения счётчиков. Проверяется взаимно однозначное соответствие существующего журнала и уже подтверждённого lifecycle-сопоставления. Допуск 0,031 секунды компенсирует только сохранённое округление `min` до трёх знаков.

## Сохранение и отображение

- Версия парсера v10 добавляет `ward_lifetimes`; прежние поля v9 сохраняются.
- Невалидная структура отклоняется до замены сохранённого JSON. Старый кэш не может понизить версию парсера, а тонкое обогащение сохраняет имеющиеся наблюдения.
- Режим «Варды на минуте» показывает только конечные подтверждённые интервалы. Пропуски и неизвестные интервалы не соединяются.
- Время ползунка ограничено точной длительностью. Округление браузером не должно удалять варды на финальной границе.
- Ссылка содержит время, режим, фильтры и стабильный `wardId`.

Основные проверки: Go `ward_lifetimes_test.go`; TypeScript `test-ward-lifetimes.ts`, `test-ward-map-link.ts` и `test-match-vision.ts`. Перед ретропереразбором делается согласованный SQLite-бэкап; после него сравниваются прежние поля, APM, KDA, результаты, API-снимки и сохранность архивов.
