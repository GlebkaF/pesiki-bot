# Независимая ветка: польза, observability и доказательство качества

Дата исследования: 2026-10-06. Это проект экспериментов, а не утверждение об уже доказанной пользе. Изучены src/advice-context.ts, advice-model.ts, live-advice.ts, profile-insights.ts, player-profile.ts, docs/live-advice-research.md, docs/replay-combat.md. Продукт не изменён.

## Что в текущем коде действительно важно

- canAdvise проверяет 10 игроков, freshness<90s и detailed, но не доказывает наблюдаемость данных для играющего. AdviceContext содержит инвентарь, уровни, netWorth обеих команд. Неизвестны роль, тайник/курьер, facet, cooldown, причины смертей и видимость.
- Prompt просит различать своих/чужих и учитывать исключения; validator проверяет IDs, длину, часть упоминаний союзников. Между «текст прошёл» и «совет механически верен» большой разрыв. BKB oversell и team/self dispel не решаются форматом JSON.
- validateAdvice отклоняет пустой players как ошибку. Правильное воздержание следует сделать отдельным успешным исходом, с кодом причины и доступными следующими действиями.
- Кандидаты обрезаются до32 по компонентам и профессиональной популярности, GENERAL_ITEMS; cost>=1000. Оценка качества одного ответа не замечает систематически отсутствующих дешёвых/нестандартных правильных решений.
- История профиля смешивает feed, API и replay, учитывает coverage; replay combat хранит входящий урон последних8s с complete, но complete не означает полноту причин смерти. Нельзя автоматически заключить «предмет точно спасал» по damage table.

## EVAL-1. Совет только по наблюдаемому игроком контексту

**Польза:** индивидуальная рекомендация не превращается в разведку через spectator data. **Данные:** на каждом факте source, gameTime, observedAt, audience, visibility: public/own/ally-confirmed/enemy-observed/spectator-only/unknown. Отдельные DTO playerAdviceContext и spectatorContext. Составы и механики допустимы; enemy inventory/экономика из всеведущего feed не становятся player-visible из-за120s задержки. История врага может влиять на выбор предмета, даже если его имя не написано в объяснении.

**Основание:** Valve в [Cheaters Will Never Be Welcome in Dota](https://www.dota2.com/newsentry/3677788723152833273) описывает бан за софт, читающий внутреннюю информацию клиента, недоступную в нормальном игровом процессе. Это конкретное заявление о client exploits, не прямой вердикт о server-side DotaTV advisor. Из него нельзя вывести ни запрет любого совета, ни разрешение нашего решения. Проектный вывод: отделять spectator analytics от помощи играющим и не полагаться на скрытые данные. Разрешённость конкретного режима при необходимости уточнять у Valve; не объявлять гарантию отсутствия риска.

**Предположение:** составы, свой инвентарь и выбранная роль уже дают полезные узкие решения. **Контрпример:** скрытый у врага Silver Edge меняет ответ на защитную сборку, хотя в тексте нет утечки; endpoint воздерживается от координат, но всё равно использует недоступные вещи. **Эксперимент:** парные fixtures отличаются только spectator-only enemy items/positions/netWorth; player output и набор фактов неизменны, spectator output может различаться. **Go:** 100% инвариантность проекции и отсутствие скрытых оснований в adversarial suite. Если невозможно подтвердить видимость — исключить поле, не «доверить prompt». **Цена ошибки:** unfair information, потеря доверия, потенциальный риск аккаунта; юридический/Valve статус не проверен.

## EVAL-2. Проверяемая следующая покупка вместо полного билда

**Польза:** один реальный выбор с проверенным эффектом и условной альтернативой. Нужны свой инвентарь, роль (может быть self-report), источник механики, исключения, собственная доступная экономика, компонентная схема. Роль не выводить из slot. Advice = objective + action + evidence IDs + applicability + exceptions + expiry, текст рендерить из разрешённых claims; свободная LLM редактура не должна вводить новые claims.

**Основание:** реальные ошибки ally Weaver/BKB/Greaves + слабый текущий validator. [Human-AI Interaction Guidelines, CHI2019](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/) даёт основание делать ограничения и исправление доступными; не доказывает эффективность Dota-советов. **Предположение:** механически верный условный выбор чаще полезен, чем универсальный билд. **Контрпример:** предмет правильно снимает debuff, но игрок нужен как damage dealer; дорогой utility задерживает win condition. Валидная механика не равна лучшему действию.

**Эксперимент:** 60 decision points из разных матчей, не60 соседних snapshots одного матча. Два независимых сильных игрока до просмотра output задают допустимое множество действий, неподходящие и дополнительные необходимые сведения. Сравнить три слепых варианта: popularity baseline, rules+template, rules+LLM. **Go для пилота:** ноль критических factual/side/effect ошибок; ≥80% ответов «приемлемо для показанного контекста», LLM побеждает template по понятности/полезности хотя бы на10п.п. без роста ошибок. Это продуктовый порог, не статистический закон; при60 случаях остаётся значительная неопределённость. **Цена ошибки:** тысячи золота/сломанный темп; хуже отсутствия совета.

## EVAL-3. Задержкоустойчивые решения и expiry по смыслу

**Польза:** совет не устарел до чтения. Нужны последовательные снимки, возраст, DotaTV delay, provenance, действия покупки, версия плана. Snapshot fresh<90s не значит настоящее. Объявленный SourceTV delay120s не доказывает, что GetRealtimeStats отстаёт ровно на тот же интервал. Реальную задержку API надо измерить; не складывать поля без проверки семантики и не считать время дважды. Нет данных определить «сейчас безопасный момент», «на смерти» по старому кадру.

**Основание:** наш наблюдаемый feed; HAI guideline timing относится к потребности пользователя, а не фиксированному cron. **Предположение:** состав-зависимый defensive choice живёт минуты. **Контрпример:** игрок уже купил предмет в нынешней игре, пока snapshot показывает старый; команда проиграла драку, стратегия резко изменилась. **Эксперимент:** выдавать совет с cutoff t, сначала добровольный clock-alignment тест сопоставляет игровой clock/инвентарь и API с eventTime/receivedAt; затем эксперт оценивает применимость в t+measuredLag и стресс-сценариях120/180/240s (future доступно только evaluator); считать долю obsolete-before-display, contradiction/churn, полезное время жизни. **Go:** ≥90% ещё пригодны на фактическом p90 end-to-end lag; ноль «сейчас жми/иди»; superseded советы не появляются после новых. Число90% — исходный gate для пилота, калибровать. **Цена:** бесполезное отвлечение и реальный вред от старого приказа. Стабильные идеи показывать как условный план; тайминги драки не поддерживать.

## EVAL-4. Воздержание оценивается вместе с полезным покрытием

**Польза:** отвечать только когда достаточно оснований, сохраняя полезность продукта. Данные: decision opportunities, reason codes abstention (role_needed, mechanics_unverified, context_stale, no_material_change, no_supported_action), версия policy, проверенные основания. Не confidence=«LLM сказала0.92».

**Основание:** [Geifman & El-Yaniv, Selective Classification](https://arxiv.org/abs/1705.08500) изучает обмен risk/coverage в классификации; его статистические гарантии напрямую не переносятся на генерацию Dota-советов. Проектная аналогия: измерять ошибки среди выданных и долю случаев, где выдано. **Предположение:** uncertainty gates коррелируют с ошибками; это надо калибровать. **Контрпример:** система безопасно молчит почти всегда, или выдаёт тривиальное «не умирай» везде — metrics без useful coverage выглядят отлично.

**Эксперимент:** один frozen test set с экспертно размеченными opportunities и not-enough-data; risk-coverage curve на нескольких gate настройках, по Turbo/role/patch отдельно. **Go:** критические ошибки0 на gate corpus, минимум50% expert-answerable opportunities получают содержательный допустимый ответ; ниже — продукт не готов, а не «безопасно завершён». На реальном holdout ≥300 независимых/кластерно учтённых случаев с0 failures дают ориентировочную верхнюю95% границу около1% при независимости; не обещать её для коррелированных кадров. **Цена:** silent failure и разочарование либо вредный совет.

## EVAL-5. Игрок выбирает проблему и получает объяснение, которое можно проверить

**Польза:** один tap «нужен сейв / не хватает урона / что следующим?» даёт отсутствующее намерение, роль и критерий оптимальности. Не вынуждать заполнять анкету в драке; optional explicit preferences до игры, карточка под катом и /advice по запросу. Отдельно «уже купил», «не подходит», «неверная механика»; dislike не означает доказанный tactical error.

**Основание:** [Buçinca et al.,2021](https://www.eecs.harvard.edu/~kgajos/papers/2021/bucinca2021trust.shtml), эксперимент199 участников: когнитивные вмешательства уменьшили избыточное следование AI по сравнению с простыми объяснениями, но получили хуже subjective ratings. Это не Dota-эксперимент; перенос ограничен. **Предположение:** малое уточнение задачи полезнее длинной уверенной прозы. **Контрпример:** игроку некогда вводить, он выбирает неверную причину проигрыша; подтверждение проблемы не подтверждает механизм.

**Эксперимент:** offline игровые сценарии с владельцами стака: 1) сразу готовый совет,2) один выбор намерения,3) короткий self-proposed item then comparison. Не вставлять намеренно неправильные советы в настоящую игру; только тестовый сценарий. **Go:** median чтение/выбор<10s; пользователи могут воспроизвести условие/исключение ≥80%; ошибочное следование в искусственно ошибочных кейсах снижается относительно explanation-only; enjoyment не падает. **Цена:** distraction/annoyance; forced training UX может убить «кайф». Сохранять необязательность.

## EVAL-6. Личная память — подтверждаемые привычки и preference, не диагноз по win rate

**Польза:** перед игрой одна конкретная привычка, после игры один разбор с2–3 клипами/таймкодами. Live memory допускает self-reported preference/role; выводы replay сначала review. Нужны source/coverage, герой/режим/патч, opportunity denominator, timestamps, complete flags, прекращение релевантности.

**Основание:** наши replay docs явно не восстанавливают fog of war,8s damage window не доказывает контрфактическое выживание; profile API смешивает источники. **Предположение:** повторяемые измеримые действия изменяемы и интересны игроку. **Контрпример:** 3смерти без BKB могут быть сознательным buyback trade; 0 wards placements — parser coverage, а не бездействие; проигрыш против Axe на3матчах не личная слабость.

**Эксперимент:** вручную проверить20 proposed memories по replay evidence, спросить игрока «похоже/не похоже»; одинаковый вывод должен иметь explicit observations и plausible alternatives. Разделять fact («в4 из6 доступных эпизодов…») от hypothesis («возможно стоит потренировать…»). **Go:** ≥95% factual traceability; ноль личных диагнозов без основания; ≥70% пользователю полезно/узнаваемо; память можно исправить/забыть. Числа продуктовые для пилота. Не делать causal claims даже при этих порогах. **Цена:** несправедливые обвинения, ложные привычки, потеря желания играть.

## EVAL-7. Командная координация как добровольный план, а не глобальный оптимум

**Польза:** договориться о следующем utility item, чтобы наши не задублировали дорогой эффект. Нужны наши intentions/acknowledgements, текущие видимые предметы союзников, роли, budget estimates; не воспринимать missing item как «никто не собирает». **Предположение:** лёгкое соглашение снижает случайные дубли. **Контрпример:** два одинаковых предмета иногда полезны; случайный союзник уже везёт ауру; богатый наш обязан закончить свой темповый item. Поэтому hard-ban всех дубликатов неверен.

**Эксперимент:** 15 исторических игровых эпизодов (или минимум сколько доступно) blind coaches оценивают coordination suggestions vs individual advice;10 consented матчей с отметкой «я собираю X» и регистрацией resolved/unresolved конфликтов. **Go:** не меньше70% coordination suggestions экспертно уместны, никакого принуждения/false certainty про союзников, реальный пользователь подтвердил ≥3 полезных предотвращённых конфликта. Это usability evidence, не win-rate proof. **Цена:** ломает личный план ради формального diversity score. Prioritise после individual gates.

## Как оценивать систему, чтобы не обмануть себя

1. Единица качества — decision opportunity и выполненная проверяемая потребность. Независимая единица эксперимента — матч/игровая сессия, не каждый совет: наши игроки взаимодействуют. Разделить train/dev/test по матчам и времени; не тестировать новую prompt на кейсах, по которым её исправляли, без нового holdout.
2. Dataset: Turbo отдельно от ranked; our supports/cores/unknown-role; выигрывающие/проигрывающие; low/high economy; начатая покупка; курьер unknown; missing mode/patch; allied hero threatens misclassification; BKB pierce; self/team dispel; already owned/upgraded; источник устарел; новое обновление; неполный snapshot. Дешёвые semantic mutation tests дополняют, а не заменяют реальные полные матчи.
3. Expert labels: два независимых оценщика не знают автора. Сначала факты/механики (correct/false/unverifiable), затем действия (good/acceptable/unnecessary/harmful/not-enough-data). Множество допустимых решений, не единственный item. Разногласия о стратегии — ambiguity, не автоматически model error; disagreement о механике решается authoritative source/игровым тестом. Арбитраж сохраняется и оригинальные оценки тоже. Нельзя majority vote считать физическим доказательством.
4. Нужны baseline template и popularity; randomized order; отдельно blind text quality и содержательная correctness. Long fluent output не получает бонус за объём. Считать critical error/card, unsupported claim/claim, coverage/opportunity, obsolete-before-display, duplicate semantic advice, role/mode slice failures, decision usefulness, time spent, irritation и costs. Деноминаторы публиковать.
5. Два режима evaluation: as-of-t correctness по информации, доступной в момент решения; retrospective outcome отдельно сfuture. Не оценивать «плохой совет», потому что проиграли после него, без причинного доказательства. Human hindsight bias тоже контролировать: скрыть итог в основной оценке.
6. Win rate маленького стака — шумный быстрый KPI: matchmaking, герои, патч, настроение, party mix, выбор когда открыть совет, learning, survival/wealth selection и shared team exposure. Даже идеализированное обнаружение50%→55% при независимых группах потребует порядка1.5тыс. матчей на группу для80%power/5%alpha; кластерность ухудшает. Это порядок по нормальной аппроксимации, не готовый power analysis. Несколько побед не доказательство.
7. Историческая покупка и победа не ответ на «помогла бы другая»: item bought зависит от доступного золота, врагов, навыка и планов. [Li et al. offline contextual-bandit evaluation](https://arxiv.org/abs/1003.5956) показывает специализированный replay evaluation при корректном logging/randomization. У нас нет propensity выбора предметов и полноценного action support; не применять IPS/DR с выдуманными propensity. Совет игроку не равен действию игрока; частичный adherence и многократные решения требуют более сложной causal модели. Current practical use replay — экспертная правдоподобность и ошибки, не causal uplift.
8. Настоящий пилот — по сессиям randomize offer advice vs usual UX, intention-to-treat, заранее primary endpoint «полезные проверенные решения без critical errors», voluntary usage и annoyance secondary. Для малого стака качественные интервью и reason-coded feedback честнее заявлений+MMR. Непросмотренные советы не считать rejected; changed mind не автоматически harmful.

## Приоритет после самостоятельной критики

Оставить ядром EVAL-1/2/3/4. EVAL-5 минимальным необязательным уточнением. EVAL-6 начинать сpostgame доказуемых эпизодов и review, не автоматической психологизации. EVAL-7 только когда известны намерения и есть реальные кейсы пользы. Выкинуть: единый win-rate score качества; постоянно болтающий coach; диктат действий из120s feed; LLM self-confidence; «у нас RAG, значит правильно»; auto-каузальные выводы из покупок победителей; рейтинг личности по KDA; умножение обычных timing benchmarks на коэффициентTurbo.

Перед evaluation нужен extractor report на каждом выбранном episode: какой игрок, интервалы покрытия, unknowns, source version, match-level holdout; as-of inventory восстанавливать сучётом продаж/разборки/передач и unknown stash, а не только последовательности purchase.
