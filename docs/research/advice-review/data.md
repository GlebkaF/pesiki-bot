# Независимая ветка DATA — данные, статистика и причинность

Проверено 2026-10-06. Это исследовательский материал, не готовая спецификация и не утверждение о качестве нынешних советов.

## Подтверждённая база

1. `src/advice-context.ts` сохраняет gameMode, но role всегда null, нет подтверждённого patch/facet. `buildCandidates` складывает события покупок четырёх фаз, сортирует сначала по наличию компонентов, затем по popularity и обрезает до 32. Следствие: генератор может вообще не увидеть подходящий редкий предмет. `GENERAL_ITEMS` — ручной набор, не проверенная онтология механик. В LLM идёт весь каталог возможных способностей героя, а не изученные/доступные способности текущего экземпляра.
2. OpenDota `getHeroItemPopularity`: до 100 последних player_matches героя с `version IS NOT NULL`; нет фильтров patch/mode/role/opponent. Возвращает счётчики событий, не denominator, состав cohort или confidence. API документирует профессиональные игры. Нельзя утверждать «41% покупают» по счётчику 41. SQL: https://github.com/odota/core/blob/e0847d8edcf33b7467860689b3277f91c1062103/svc/util/queries.ts#L49 . Спецификация https://docs.opendota.com/ .
3. `itemTimings` агрегирует purchases >=1400 в интервалы 7.5,10,12,15,20,25,30 минут и wins. Запрос группирует по hero/item/time; режим/роль/патч не возвращаются. Отбор scenarios берётся из auto-parsed игр, код прямо отмечает неслучайность. https://github.com/odota/core/blob/e0847d8edcf33b7467860689b3277f91c1062103/svc/util/scenariosUtil.ts ; https://github.com/odota/core/blob/e0847d8edcf33b7467860689b3277f91c1062103/svc/util/insert.ts#L435 . Это описание выборки, не основание ранжировать покупку по приросту побед.
4. `getHeroBenchmarks` в том же queries.ts имеет bracket и core/support, причём комментарий ограничивает filtered sets non-Turbo. Даже новые role benchmarks не дают item-build policy для Turbo. Ссылка выше #L111.
5. Используемый Steam terse schema содержит inventories, networth, gold, levels, KDA, ability IDs, mode и время. Нет cooldown, ward vision, ability levels, facet, patch, courier/stash completeness. Более богатый realtime protobuf не доказывает доступность richer fields endpoint. https://github.com/SteamDatabase/Protobufs/blob/master/dota2/dota_gcmessages_common.proto . Сам mirror — описание протокола сообществом, фактический runtime контракт важнее.
6. Локальные сохранённые JSON `data/replays/*.json`: 78 матчей, из них 73 mode_23; 780 player records, у всех непустые item_timings, но 0 match start_time, 0 combat_timeline, 0 death_journal, 0 item_uses. `src/replay.ts` и SQLite store теперь умеют больше, но наличие типов не доказывает заполненность исторических данных. Это НЕ аудит production SQLite. Нужна отдельная coverage inventory по источнику/версии парсера/матчу.
7. STRATZ официально предлагает API: https://stratz.com/api и https://api.stratz.com/graphiql . Публично просмотренные страницы не дали схемы, авторизованный запрос не выполнялся. Не подтверждены конкретные Turbo/patch/role фильтры, ставки лимитов или полнота item events. Считать исследовательским кандидатом, не готовой заменой.
8. Статическая библиотека dotaconstants закреплена ревизией, но commit hash не означает patch certification каждой механики. https://github.com/odota/dotaconstants . Критичные взаимодействия требуют официального patch diff и/или игрового теста; live сообщает неизвестный patch.

## Почему хороший win rate предмета может дать плохой совет

Это наши выводы из структуры данных, а не установленная причинность Dota-исследованием. Богатые/выигрывающие игроки раньше покупают дорогие предметы; проигравшие до нужной минуты их не успевают купить. Контрпредмет берут в особо тяжёлых драфтах и его сырая статистика выглядит хуже. Предмет зависит от роли, опыта героя, союзной коммуникации и будущего плана. Final inventory содержит будущее относительно момента рекомендации. Поиск максимального win rate среди многих предметов усиливает случайный шум. Профессиональные и Turbo матчи отличаются процессом принятия решений, а не только скоростью часов.

Методологическая опора: Hernán et al. требуют согласовать eligibility, assignment и time zero при оценке вмешательства из наблюдений; отнесение в группу по будущему действию создаёт selection/immortal-time bias. Применение к Dota — наша аналогия, не готовая доказанная модель: https://pmc.ncbi.nlm.nih.gov/articles/PMC5124536/ . Для нас baseline = конкретный момент, когда игрок действительно может выбрать один из доступных планов, а не завершённый матч.

## DATA-1. Контракт пригодности данных перед каждым семейством советов

**Гипотеза/польза.** Отдельная проверка достаточности входа на каждый тип решения уберёт большую часть уверенной чуши, сохранив полезные варианты. Item planning допускается с mode+hero+inventory и оговорённой неизвестной ролью; минута-бенчмарк требует точного cohort; контрмеханика требует проверенного rule revision; tactical engagement требует данных, которых у нас сейчас нет.

**Данные/доступность.** Есть snapshots и source timestamps; добавить observedAt vs receivedAt, field coverage, patchKnown, modeKnown, roster identity, missing inventories, revision. Источник patch должен быть отдельным: не выводить его только из сегодняшней даты. Доказательства 1,5,8.

**Допущение.** Пользователь предпочитает условный полезный совет/пропуск уверенной ошибке. **Контрпример.** Слишком жёсткий gate заглушит почти всё, потому что точный patch неизвестен. Поэтому gate по claim/rule, а не глобальный all-or-nothing.

**Дешёвый решающий эксперимент.** 40 сценариев missing/stale/delta/mode/unknown facet + 40 валидных; один и тот же факт последовательно удаляется. Каждый вывод обязан показать, какие сведения он использовал. **Go:** 0 unsupported tactical/timing assertions, не менее 90% валидных стратегических решений сохраняются. Это проектный threshold, не научно подтверждённое число. **No-go:** приходится угадывать обязательные поля. Сложность низкая-средняя, ценность высокая.

## DATA-2. Покупки OpenDota — prior для recall, а не ранжирующий oracle

**Гипотеза/польза.** Объединение трёх независимых источников кандидатов — hero popularity, проверенные решения угроз, завершение имеющихся компонентов — повышает шанс включить подходящий выбор без объявления популярности качеством. У каждой корзины собственная квота; редкие защитные предметы не вытесняются popularity top-32. После этого механический veto и ranking по конкретной задаче игрока.

**Доступность.** Все необходимые данные уже частично есть. Нужны role-conditional безопасные core/support fallback builds, поскольку нынешний fallback GENERAL_ITEMS состоит преимущественно из utility/defense. Компонент не должен автоматически победить лучшую смену плана. Доказательства 1,2.

**Контрпример.** Invoker core и support с одинаковым draft требуют разного; недорогой готовый предмет может быть лучше завершения ошибочной покупки. Без role не выдавать обязательный выбор.

**Эксперимент.** 60 вручную размеченных decision snapshots, включая минимум 20 редких counters/компонентных ловушек; независимый сильный игрок указывает 2–3 допустимых предмета до показа генератора. Сравнить candidate recall старого top32 и нового объединения. **Go:** допустимый выбор присутствует >=95%, illegal/owned=0, rare-counter recall выше baseline; **No-go:** расширение списка лишь грузит LLM, качество выбора не растёт. Сложность средняя; отдельная дешёвая победа без большого dataset.

## DATA-3. Turbo cohorts только как описательные ориентиры, без обещания uplift

**Гипотеза/польза.** Собственные и доступные parsed Turbo матчи, разделённые по режиму, широкому patch epoch, hero и достоверной роли, позволят узнавать нормальные планы и диапазоны экономики нашего стака. Экономическое состояние лучше голой минуты; сравнивать на decision time, не final inventory.

**Данные.** Local имеет 73 Turbo, но start_time отсутствует — patch assignment сейчас невалиден; production coverage неизвестен. OpenDota агрегаты недостаточны, нужны raw records с timestamps и purchase logs, плюс cohort metadata. Не склеивать редкую роль из 3 матчей с pro median под общей подписью «обычно».

**Контрпример.** 73 общих матча превращаются в 1–3 на hero/role/patch; ближайшие соседи формально похожи, но совсем иной draft. Сложная модель выдаст красивый шум.

**Эксперимент.** Coverage audit на имеющейся базе: таблица eligible counts и missingness; leave-one-match-out retrieval с оценкой человеком релевантности 20 соседей. **Go:** по минимум 3 часто играемым hero/role группам >=30 сравнимых матчей и >=80% retrieved contexts сочтены полезными; показывать медиану/IQR/n, не оценки «опоздал». **No-go:** мало данных/неизвестный патч — сохраняем только собственные описательные примеры, никаких timing judgments. Сложность средняя-высокая, не блокирует DATA-1/2.

## DATA-4. Персонализация из подтверждённых эпизодов, не психологический профиль

**Гипотеза/польза.** Короткое «напоминание твоего повторяющегося риска» полезнее ещё одного общего build. Например, в нескольких подтверждённых эпизодах предмет был куплен, но его применение не зарегистрировано перед смертью — запросить проверку/обучающий разбор, а не утверждать забывчивость.

**Данные.** Нужны event-level item uses/ready states, death journal, контроль/урон, coverage и identity. Нынешние local JSON этого не содержат; суммарный item_uses тоже не доказывает готовность в конкретную секунду. В store поля существуют, наполнение надо аудитить. Доказательства 6.

**Контрпример.** Предмет был на cooldown, silence/disable, в backpack, недоступен или применение не помогло бы. «Не нажал BKB» без состояния — ложный диагноз.

**Эксперимент.** 20 candidate episodes с ручной проверкой replay, ослеплённой к предлагаемому выводу. **Go:** 0 ошибочных событий в обязательных фактах; для формирования повторения минимум 3 проверенных независимых эпизода и нормировка на число доступных opportunities; игрок оценивает reminder полезным. **No-go:** нет ready-state, выдаём только наблюдение о зарегистрированных событиях, не miss-opportunity. Сложность высокая; позже, не первая live функция.

## DATA-5. Decision journal для честного offline eval и будущего обучения

**Гипотеза/польза.** Сохранять ровно доступный в момент решения контекст и границы неизвестного важнее закупки ещё одного API. Позволяет воспроизводить ошибки, сравнивать модели, не подсматривать будущее и учиться на настоящих вопросах стака.

**Данные.** Снапшот, availableAt/eventTime, input revisions, rule IDs, candidate set, output/rejection, optional user feedback; outcome хранить отдельно. Текущий live service в основном держит совет в memory и бюджет на disk; полного decision ledger не видно.

**Контрпример.** Лог становится складом персональных данных и никто его не размечает; 100 снимков одного матча ошибочно считают 100 независимыми тестами. Разделять train/test целыми матчами и временем, ограничить retention и писать schema/version.

**Эксперимент.** На 10 матчах воспроизвести 100% решений только из ledger; проверить отсутствие future events через poisoning fixture с будущим большим предметом. **Go:** outputs reproducible, split by match, provenance complete; **No-go:** golden benchmark использует финальный purchase_log как текущий инвентарь. Сложность низкая-средняя, старт немедленно.

## DATA-6. Оценивать causal пользу рандомизацией показа, а не item win rate

**Гипотеза/польза.** Сравнивать адаптированный совет против простого проверенного baseline на уровне целого матча/сессии. Промежуточные метрики: useful/not useful с причиной, выполнимость, конфликты, повторяемость. Победы — secondary exploratory metric до накопления достаточной мощности.

**Данные.** После quality gates DATA-1/2/5: opt-in пилот, случайное назначение по матчу или коротким блокам, соблюдение одной политики для всего стака из-за team interference; logging displayed/seen/accepted отдельно. Нельзя рандомизировать по игроку внутри одной команды и считать independent.

**Контрпример.** Пользователь выполняет советы только когда уже выигрывает; корреляция accepted advice с wins снова confounded. Показ не равен compliance, поэтому основной анализ intention-to-treat, плюс honest descriptive acceptance.

**Эксперимент.** 20–30 матчей feasibility, заранее фиксированные primary usefulness/errors/burden, без претензии доказать win-rate lift. **Go:** unsafe/mechanically false=0 на ручном аудите, полезность адаптированного варианта выше baseline и noise burden не растёт; **No-go:** only victory metric или winner-picked examples. Для win-rate evidence нужен отдельный power calculation; маленький стак быстро его не обеспечит. Сложность организационная средняя, вычислительная низкая. Методологическая опора — target trial статья выше.

## DATA-7. STRATZ — короткий capability spike, не зависимость архитектуры

**Гипотеза/польза.** Если авторизованный API даст raw item events + patch/mode/position filters с достаточным покрытием Turbo, он быстрее улучшит DATA-3, чем массовый самостоятельный replay parsing.

**Данные/статус.** Официальная API страница существует; фактический рабочий query и лицензия такого reuse не проверены. Не повторять ошибку meta.ts с угаданными endpoints и эвристическим JSON.

**Контрпример.** Schema предлагает filters, но сочетание Turbo+position пустое, limits слишком малы, role inferred from final farm и даёт future leakage. Название поля не доказательство валидности.

**Эксперимент.** После обычной авторизации одна schema introspection и 3 точечных query на известные свои матчи: mode23 и предметы/время сверить с local replay; документировать actual coverage, patch granularity, semantics, limits, terms. **Go:** >=95% точность ключевых событий на проверенных примерах и usable Turbo cohort metadata, доступ устойчив/разрешён; **No-go:** обход ограничений, неподтверждённая семантика, агрегаты без denominator. Сложность spike низкая; полноценная интеграция средняя. Не блокирует OpenDota baseline.

## Предварительный отсев

Строить сейчас DATA-1, DATA-2, DATA-5. DATA-3 только после coverage gate; DATA-6 после ручного качества. DATA-4 отложить до подтверждённых событий. DATA-7 ограничить spike, не обещать пользу заранее. Отвергнуть: raw highest-winrate items; Turbo=обычный тайминг/2; position=team_slot или final farm без проверки; уверенные советы на неподтверждённом patch; обучение на final inventories как на decision snapshots; эффект совета из wins среди выполнивших совет; модели «персонального стиля» из нескольких матчей.

## Коррекция семантики delay от root

SourceTV lobby `game.delay=120` — номинальная задержка трансляции, а не проверенная задержка GetRealtimeStats. Не заявлять `delay + snapshot age` как измеренный factual lag этого endpoint. Нужна paired calibration gameclock/events игрока vs API timestamp/game_time. DATA-1/5 должны различать nominal spectator delay, receivedAt, source timestamp и неизвестную semantics; source lag до калибровки unknown.
