# APM из реплеев

`/analyze` выводит APM матча в строках «НАШИ», страница разбора — также в таблице игроков.
`/stats` берёт среднее арифметическое APM матчей выбранного периода из SQLite и показывает покрытие,
например `APM: 185 (2/3 матчей)`. Отсутствующие значения не считаются нулями.
Прежний all-time APM из OpenDota больше не подставляется в статистику дня/недели/месяца.

## Определение

Версия `spectator-orders-v1`: одно сообщение `SpectatorPlayerUnitOrders` = одна команда,
независимо от количества выделенных юнитов. Повторные команды тоже считаются.
Учитывается интервал от первого combat-log GAME_STATE 5 до первого GAME_STATE 6.
`floor(actions * 60 / duration_seconds)`, с точной длительностью, без округления до минут.
Контроллер сопоставляется с назначенным героем через entity handle, не по номеру слота.
Если поток отсутствует, матч не завершён или привязка команд к игроку не разрешилась,
APM отсутствует. Это количество команд, а не показатель скилла; равенство методике OpenDota не обещается.

## Хранение и сбор

Файл `data/stats.sqlite` (переопределяется `APM_DB_PATH`; базовый каталог — `DATA_DIR`).
В Docker он находится в существующем постоянном томе `pesiki-data`.
Таблица `player_match_apm`: match_id, account_id (Steam32), hero, start_time (Unix seconds),
actions, duration_seconds, apm, version, parsed_at (Unix milliseconds).
Первичный ключ `(match_id, account_id, version)`; повторный разбор обновляет запись транзакционно.
История без TTL, переживает пересоздание контейнера. Исходные `.dem` по-прежнему удаляются после разбора.

APM сохраняется для всех опознанных игроков при разборе, до обращения к LLM.
Фоновая синхронизация ленты (раз в 5 минут) ставит в сбор недостающие реплеи за последние 7 дней
из последних 12 матчей каждого отслеживаемого игрока. `/stats` также ставит свежие пропуски в очередь.
Сбор идёт последовательно, без вызова LLM и без отправки сообщений в Telegram.
Свежие недоступные реплеи повторяются не чаще раза в 10 минут. Реплеи без пригодного потока — раз в сутки.
Очередь восстанавливается обнаружением матчей при синхронизации ленты после перезапуска.

Первая выдача `/stats` может показать неполное покрытие, пока идёт сбор.
Старые JSON без APM автоматически переразбираются для свежих матчей.
При ручном `/analyze` тоже пробуем обновить старый кэш; если реплей уже недоступен,
сохраняется доступный разбор с `APM —`. В сохранённые разборы APM подставляется из БД при чтении.
Восстановить APM удалённого реплея из старого JSON, где команды не сохранялись, нельзя.

## Проверка

- `npm run build`
- `npm run test:apm`
- `cd tools/replay-parser && go test ./... && go build -o replay-parser .`
- Опционально: распарсить матч 8994933487 новым бинарником и передать JSON через
  `APM_TEST_REPLAY_JSON=/path/to/result.json npm run test:apm`.

Проверенный матч 8994933487: 38 750 команд за 1064.9333953857422 с,
zladey 185, Shootema 123, Marinad 147 APM. Также проверен публичный реплей 8552595443.

Бэкап живой SQLite делайте через SQLite backup API/`.backup`, чтобы учесть WAL.
Не копируйте только основной файл открытой базы без WAL.
Используемый драйвер: [better-sqlite3 API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md).
