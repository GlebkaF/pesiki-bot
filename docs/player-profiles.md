# Профили игроков

`/players` — все 14 игроков, поиск по нику. `/player/<Steam32>` — профиль.
Периоды: `?period=7`, `30`, `all` (по умолчанию). Семь и тридцать дней — скользящие
интервалы от текущего времени. Матчи без даты входят только во всю историю.
Даты на профилях показываются по Москве. Это накопленная выборка, не вся карьера.

Профиль показывает результат, героев, средний и медианный APM, график по матчам,
состав команд, совместные игры на одной стороне, время начала игр, максимум APM,
самую длинную игру и историю с пагинацией по 10 карточек.
`?hero=<hero-name>#history` фильтрует только историю матчей по герою.
`?chart=<match_id>#tempo` сохраняет выбранную точку графика.
Разделы имеют постоянные якоря: `#apm`, `#tempo`, `#heroes`, `#partners`, `#rhythm`, `#history`, `#method`.
Кнопка рядом с заголовком копирует ссылку вместе с текущими параметрами.
`?match=<match_id>#apm` выбирает подробности одного матча; параметры периода сохраняются.
Для отсутствующего измерения используется прочерк, измеренный ноль остаётся нулём.

## Источники и постоянное хранение

Все таблицы находятся в существующей `data/stats.sqlite`, без TTL:

- `player_match_apm`: прежние итоговые значения; формула `spectator-orders-v1` не менялась.
- `player_match_actions`: исходный словарь типов команд по матчу/аккаунту/версии.
  При записи проверяется неотрицательность целых счётчиков и совпадение суммы с `actions`.
- `player_match_results`: ответы успешных запросов последних матчей OpenDota.
  Старый `feed.json` импортируется с отдельной меткой `feed` и не может переписать
  подтверждённый ответ `opendota`. Сырые KDA боевого лога в профиль не подставляются.
- `profile_rosters`: компактная проекция сохранённых реплеев (ID, дата, длительность,
  исход, SteamID/герой/сторона). Существующая история мигрирует автоматически;
  следующие разборы обновляют её. Полные боевые события при открытии профиля не читаются.
- `parsed_replays`: полный JSON сохраняется как прежде, теперь с `action_counts`.

Страницы не вызывают OpenDota и не запускают разбор реплеев. Собранные профили
кэшируются в памяти на 15 секунд. Часовая синхронизация ленты остаётся прежней.
Новые таблицы автоматически входят в штатный online backup SQLite.

Совместная игра определяется по стороне в реплее, не по совпадению ника и не по
присутствию двух игроков в ленте. Это не подтверждение party и не причинный эффект
напарника. Публичная страница получает только Dota-ник и игровые данные: Telegram ID,
дни рождения и внутренние заметки бота не передаются в HTML.

## Состав APM

Парсер `pesiki-replay-v3` считает тип каждого того же spectator-order сообщения,
которое уже включалось в APM. Названия типов сохраняются без потерь.
Категории определены в `src/action-counts.ts`:

- перемещения: move-to-position/target/direction/relative, patrol;
- атаки: attack-move и attack-target;
- способности и предметы: cast-команды, переключения, vector target, consume item;
- инвентарь: покупки, продажа, перенос, передача и подбор предметов;
- остальное: hold/stop, обучение навыков, руны, неизвестные типы.

Приказ не равен успешному применению или физическому клику. Приказ нескольким
юнитам считается один раз. Повторные перемещения включены. Активные предметы
и способности используют общие типы cast, разделить их этим счётчиком нельзя.

Доли — сумма команд по матчам с деталями. Частота категории — сумма её команд × 60 /
сумма точных длительностей этой выборки. Средний APM в шапке — среднее арифметическое
APM всех измеренных матчей, поэтому эти две разные выборки и способы усреднения
не обязаны совпадать. Число матчей с покрытием показывается рядом.

## Восстановление старых подробностей

Перед production-миграцией выполнить `/home/gleb/.local/bin/pesiki-stats-backup`.
Затем внутри контейнера:

```sh
node dist/backfill-action-counts.js
```

CLI последовательно переразбирает только локальные `data/replay-archives/*.dem.archive`.
Сеть не используется. Уже восстановленные матчи пропускаются. Старые APM сверяются
до записи; расхождение требует ручной проверки. Обогащённые ранее показатели
сохраняются. Временная распаковка удаляется в `finally`, исходный архив остаётся.
Повторный запуск безопасен. Завершение с ошибками даёт ненулевой exit code.

Для локальной проверки на отдельной копии данных:

```sh
DATA_DIR=/path/to/copied-data FEED_SYNC_DISABLED=1 WEB_PORT=3011 npm run web
DATA_DIR=/path/to/copied-data REPLAY_PARSER_BIN=/path/to/parser npx tsx src/backfill-action-counts.ts
npm run test:profiles
npm run test:apm
npm run test:replay-storage
npm run build
```

`FEED_SYNC_DISABLED=1` предназначен для изолированной витрины при разработке.
В production он не задаётся. Бинарный парсер проверяется `go test ./...` в
`tools/replay-parser`. Исторические общие APM без исходного реплея нельзя разложить
на типы команд; такие игры остаются в общем графике с явным отсутствием деталей.


## Разовый ретро-проход по всей известной истории

`node dist/retro-action-counts.js` обходит сначала сохранённые реплеи, затем остальные
известные матчи отслеживаемых игроков. Успешные ответы полного API сохраняются в
`match_api_snapshots` в SQLite, включая адрес исходного реплея. Повторный проход
использует эти метаданные и локальные архивы. Результаты попыток — в
`data/action-retro-report.json`; обычный часовой polling не меняется.

Запросы метаданных разделены минимум двумя секундами; при cooldown проход
останавливается. Перед новым запуском выдержать указанный сервисом cooldown.
Сохраняется резерв свободного диска 3 GiB. Недоступные CDN URL проверяются повторно
не раньше следующего дня. Временный HTTP 502 считается ошибкой, а не удалением файла.

У некоторых старых demo заголовок содержит match_id=0. Такой файл принимается только
после независимой сверки всех героев, сторон и известных аккаунтов с ответом API.
Чужой ненулевой match_id всегда отклоняется. Перенос разбивки сравнивает прежние
APM и сохраняет последнее обогащение матча под транзакционной блокировкой.

## Мобильная итерация и функции профиля по мотивам Plus

Ориентир: https://www.dotabuff.com/plus — персональные герои, матчапы и анализ реплея.
Алгоритмы и дизайн собственные; глобальный рейтинг Dotabuff не воспроизводится.

- Личный топ внутри `#heroes`: минимум 5 известных исходов, сортировка по нижней
  границе 95% интервала Wilson. KDA агрегируется по сумме убийств/ассистов/смертей,
  знаменатель при нуле смертей равен 1. Покрытие выводится отдельно.
- `#form`: последние 10 датированных игр против предыдущих 10. Дельта каждой
  метрики видна только при полном покрытии обеих десяток. Отсутствующая метрика
  не заменяется нулём, неизвестный исход не считается поражением.
- `#matchups`: результаты против героев и вместе с героями своей команды,
  минимум 3 известных исхода. Один герой учитывается максимум один раз в матче;
  собственный герой не входит в союзные матчапы. Стороны radiant/dire проверяются.
  Это командный результат, не персональный исход линии и не причинный контрпик.
  `?side=allies#matchups` сохраняет выбор вкладки.

Мобильный интерфейс проверен в Chromium и WebKit на ширинах 320/390/430, светлой
и тёмной темах: без горизонтального скролла документа, основное управление >=44px,
проверка WCAG A/AA через axe. Sticky-меню прокручивается внутри собственной строки.
История — карточки по 10, KDA/APM видны без раскрытия таблицы. Все разделы имеют
кнопки копирования ссылок с параметрами; при отказе clipboard выводится сама ссылка.
На одинаковой локальной истории начало APM поднято с 1110px до 504px от начала
страницы (390×844), удалены повторяющиеся сводные карточки перед полезным содержимым.

`#economy` читает один выбранный реплей. `?economy=<match_id>#economy` сохраняет
игру. График стоимости имущества, точки 10/20/30 минут и журнал покупок используют
сохранённые `networth_by_minute` и `item_timings`. Индекс 0 — первая минута, через
отсутствующие значения линия не проводится. Тайминг PURCHASE не означает доставку
или наличие предмета в инвентаре; decimal-минуты переводятся в секунды. Ключевые
предметы имеют локальные подписи, полный список доступен в раскрытии. На этой
странице не используется `ParsedPlayer.gpm`, вычисляемый парсером из конечного NW.
